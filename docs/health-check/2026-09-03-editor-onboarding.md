## 問題一：學者與責編共用同一份 SSOT，會出什麼事

會出事，但解法不是分成兩份。`status` 上鎖之後，核可制度已經成立。
以下是**編輯權限已經開出去的現在**，實際還開著的洞。
依「多可能發生 × 破壞多大」排序。

### 已解決 —— 學者自己把 `status` 改成 `Approved`

原報告排名第 1。**captain 回報 `status` 欄的保護範圍已設定，只有他能改。**
此風險不成立。核可制度是有效的。`docs/content-pipeline/design.md:386` 的施工項目 4
標示已過時。

**剩下的小事**：確認保護範圍是否也涵蓋**標題列**與**整列刪除**。
這兩項與 `status` 是分開設定的。見風險 2 與風險 5。

### 風險 1（高）：試算表的一格可以在網站上執行 HTML —— 現在就開著

同步完全不做淨化。**本次稽核發現有兩條路徑，不是文件記載的一條**：
`src/app/past/page.tsx:197` 吃 Track 1 的 `content`，
以及 `src/app/present/page.tsx:110` 吃 `site_tldr` 的 `label` 與 `text`。
TODO 的 P2-10 只記了前者。
刻意攻擊機率低。但**從 Word 貼上帶格式的文字就會意外觸發**。

**修法**：同步時淨化，或渲染改純文字。範圍要含第二條路徑。
`docs/health-check/TODO.md:816` 明訂這件事必須在分享試算表**之前**處理。
分享已經發生，這條前置被跳過了。**這是目前的第一優先。**

### 風險 2（高）：誤刪資料列，程式回報成功 —— 完全無防護

多人捲動四十列的表，選錯列按刪除是常見失誤。
檢查只在**一列都不剩**時才出聲。
刪掉 40 筆裡的 39 筆，程式會印「✅ 已寫入（1 筆）」、退出碼 0。
內容少了 97.5%，系統回報成功。這正是不變式 #3 要根除的靜默失敗。

**修法**：加一條「跌幅門檻」。已核可列數比上次少兩成以上就中止。
**這一條所有設計文件都沒有涵蓋，feature 040 也不涵蓋**
（指紋比的是內容有沒有變，被刪的列根本不在檔案裡）。
目前唯一能發現的方式是 PR diff。

### 風險 3（中）：核可之後才改內容，舊核可繼續生效 —— 另一位 FO 施工中

主編核可了 A 版本。編輯之後把同一列改成 B 版本。
`status` 仍然是 `Approved`。下一次同步會把**沒有人審過的 B 版本**直接送上網站。
`status` 上鎖擋不住這個。鎖的是誰能核可，不是核可之後內容還能不能動。

**修法**：feature 040，已由另一位 FO 接手。
**在它上線之前，這一條要靠使用說明擋**：已核可的列不要直接改，先請主編清空 `status`。
新版使用說明第【四】節已寫入。

### 風險 4（中）：沒有「我填完了」這個動作

`status` 只有三個值：`Approved`、`Rejected`、空白。
空白同時代表「還沒寫完」和「寫完了等審」。兩者無法區分。
學者填完之後，**沒有任何地方可以按**。
現況是責編必須自己每天巡表找新列。

**修法**：短期用群組口頭回報並指定負責人。中期決定要不要加一個 `Needs Review` 狀態。

### 風險 5（低）：改到欄位標題，整條產線停擺 —— 行為正確

程式看不懂標題會中止並指名。這是刻意設計的大聲失敗，方向對的。
但它表示**任何一個人改一個標題，所有人都發不了稿**。
而標題裡的中文說明看起來就像可以整理的東西。

**修法**：把標題列一併設保護範圍（與 `status` 是分開設定的，請確認是否已含）。
新版使用說明第【三】節已明寫不要改標題。

## 問題二：「使用說明」分頁要怎麼改

repo 裡沒有這個分頁的完整副本。
但體檢報告抄下了四條原文（`docs/health-check/2026-08-31-content-pipeline.md:147-150`）。
改寫前你仍需自己打開線上試算表對照全文。

> 1. 此檔案僅為資料人工收集區：會再複製到給機器讀取的文件，此處可自由編輯刪除，不用擔心會弄亂系統
>
> 2. Track 1, Track 2 編輯通則：粉紅底色欄位：必填／黃底色欄位：選填／其他未標色欄位：次選填（可 AI 生成後再校對）
>
> 3. Track 1 資料是我從黑客松活動整理的部分資料丟入，若有錯誤請直接改正
>
> 4. Track 2 中，希望置頂的請在 "sticky" 一欄勾選 "TRUE"

### 第 1 條是全份文件最危險的一句

「此處可自由編輯刪除，不用擔心會弄亂系統」。這句話在分表時代是對的。**現在完全錯誤。**
這張表已經直接餵給同步程式。
一位守規矩的學者讀完這句，會理直氣壯地刪列、改欄位、亂試。
而每一個動作都直接影響網站。

這不是疏漏，是**白紙黑字的授權**。不改這一條就開權限，等於在授權破壞。

### 逐條對照

| 舊說法 | 為什麼現在錯 | 應改成 |
|---|---|---|
| 「會再複製到給機器讀取的文件」 | 那份 `SSOT_Editor` 已於 2026-09-02 封存。人工複製步驟已刪除 | `SSOT_收集區` 就是唯一真相，沒有第二張表 |
| 「可自由編輯刪除，不用擔心會弄亂系統」 | 同步直接讀這張表。刪一列等於下架一筆內容 | 這張表直接連到網站。刪除或改寫已核可的列，網站會跟著變 |
| 「粉紅底色＝必填」 | 顏色機器讀不到，無法強制。這正是不變式 #6 的反例 | 改用文字逐欄列出必填。底色可留作視覺輔助，但不是規則來源 |
| 「未標色欄位可 AI 生成後再校對」 | AI 生成未校對的內容已上線過：虛構出處「某學者」掛了四個月、`test test test` 對外顯示 | 同步會擋下這些字樣。AI 生成內容必須逐字校對後才可核可 |

| 「置頂勾選 TRUE」 | 規則沒變，但現在有格式強制 | 保留，註明只能填 `TRUE`／`FALSE`／留空，其他值會讓整份同步中止 |
| （舊範本）`status` 可填 `Draft`／`Needs Review` | 現在只認三種值，填 `Draft` 會讓**整份同步中止** | `status` 只能是 `Approved`／`Rejected`／空白，而且學者不要碰 |
| （舊範本）新增 `tldr` 那一列 | `tldr` 已移出 Track 2，改為獨立分頁 `site_tldr` | 摘要區塊改在 `site_tldr` 填，一列一個重點 |
| （舊 cheatsheet）自己跑同步、自己 push 上線 | 兩者皆已禁止。部署不得執行同步 | 學者不執行任何指令，也不碰 repo |

### 新版「使用說明」開頭三句 —— 可直接貼進試算表

```
1. 這張表就是網站的內容來源。沒有第二張表，不用複製到別的地方。

2. 只有 status 欄填 Approved 的列會上線。status 欄由編輯台填，請不要動。

3. 任何一列填錯格式，整份同步會停下，所有人的更新都上不了線。
```

第 3 條最重要。舊系統從來不拒絕資料，學者沒有這個概念。
他不會知道自己一個格子填錯，會擋住所有同事的稿。

### 六條格式規則 —— 學者最容易猜錯的地方，一併貼上

```
· year 只能是 4 位數字。寫「民國87年」會讓整份同步停下。
· link 與 image_url 必須以 http:// 或 https:// 開頭。
· vibe 只能從下面清單複製貼上，不要自己打字。
· sticky 只能填 TRUE、FALSE 或留空。
· id 不可以和別人重複。新增列前先問編輯台要編號。
· 不要改任何欄位標題，不要新增同名欄位，不要刪整列。
```

`vibe` 目前接受的九個值（請複製，不要打字）：

```
🔥 公民必讀
🌍 國際視角
💬 正反交鋒
📖 深度解析
📣 懶人入門
🎯 精準短評
🔭 他山之石
💡 腦袋升級
🔥 戰火猛烈
```

注意：這九個值是程式從「目前已發布的實際值」取出來的，**不是編輯台的決定**。
線上實際只用到四種。最終清單今晚就可以請學者定案。

### 改寫前你要先裁示一件事

`docs/content-pipeline/design.md` 第二節的欄位表與 `scripts/sync-content.mjs` 有六處不一致
（必填欄位、佔位檢查範圍、`views` 格式等）。
**建議一律以程式碼為準**，因為那是實際會跑的東西。然後回頭修 `design.md`。

## 問題三：學者編輯的使用者體驗報告

以一位有 Google 帳號、會用試算表與 Word、沒有 GitHub 帳號、不用終端機的法學者為視角，
走完七步。

### 01　取得存取權（高）

目前什麼都看不到。試算表權限只有你一人。
也沒有任何入門文件是寫給學者的。
`docs/project/contributing.md` 講的是 GitHub Issues 與 Fork PR，對象是工程志工，
完全沒提試算表。
**整條旅程在第一步就不存在。**

### 02　搞懂要填什麼（高）

他讀到的是四條過時說明。其中第一條主動告訴他可以隨便改。
欄位標題的中文註解說明了「這欄是什麼」，但**完全沒說格式規則**。
所有會導致同步中止的規則，都只存在於他看不到的兩個地方。

### 03　填寫一列（高）

六個最容易猜錯的地方，其中五個的後果是「整份同步中止，所有人的內容都發不出去」。
而他不會知道是自己造成的。
最嚴重的是 `id`。**由誰指派、怎麼編號，文件完全未定義**，現有編號還跳號。
兩位學者同時新增，很可能都填同一個號碼。

### 04　宣告完成（整條產線唯一完全不存在的環節）

沒有任何地方可以按。設計裡沒有草稿／已送出狀態。
他連「把狀態改成待審」這個動作都沒有，因為 `status` 設計上他改不到。

### 05　等待與回饋（高）

完全黑箱。`reject_reason` 欄**在試算表上根本不存在**，所以退稿沒有地方寫原因。
驗證錯誤訊息寫得很好，指名哪一列、哪一欄、錯在哪。
但只印在工程師的終端機上，送不到會改的人手上。
而且一人出錯全體連坐，其他人不會收到任何訊息。

### 06　看到成果（中）

預覽是 GitHub 上的 PR 網址。
設計文件當初拒絕架 staging，理由是「編輯台決策者可以直接用 GitHub」。
**那句話講的是你，不是學者。**
一旦有學者協作者，這個前提就不成立了。

### 07　改錯字（唯一「做對事卻讓系統退化」的環節）

他發現已核可那列有錯字，直接改掉。使用說明第 3 條也是這樣教的。
`status` 不會改變，未經重審的內容會直接發布。
這正是 feature 040 要修的，而 040 還沒上線。

### 會讓學者「做對的事卻造成壞結果」的陷阱

- **相信使用說明第 1 條，放心刪列亂改。**最危險的一項，因為它是白紙黑字的授權。
- **從 Word 貼上一整段。**真正的風險不是格式，是**貼上多欄造成整批欄位錯位**。
  這正是 15 筆資料損壞的成因，也是本次事故的起點。
- **整理欄位標題。**刪註解不會壞，但打錯一個字會讓整份同步中止。
  而他會以為是自己把系統弄壞了。
- **複製一欄來備份。**兩欄同名，同步中止。`site_tldr` 已經發生過一次。
- **填一個更貼切的 `vibe` 分類。**整份同步中止。他不會知道程式裡有一份寫死的清單。
- **清空 `site_tldr` 的 `order 0` 那格。**網站首頁整個摘要區塊會消失。
  程式現在擋得住，但他不會預期一個空格子能讓一整塊版面消失。
- **在 `content` 欄貼帶標記的文字。**舊範本裡的示範資料本來就含 HTML 標籤。
  照著仿寫等於在網站上寫程式。

## 今晚：最小可行版

權限已經開出去了。所以今晚的重點不是「要不要開」，
而是**讓已經有權限的人知道規則**。以下每一句在今天都是真的。

### 今晚不要承諾的一件事

**不要說「你們填、我們自動上線」。**
目前沒有自動化，也沒有任何回饋管道。
同步要有人手動按，沒有排程。上一次的間隔是四個月。
承諾了做不到，比說清楚限制更傷信任。

### 今晚可以做的五件事

**01　發新版使用說明，並口頭講最重要的三條**
舊版第 1 條「可自由編輯刪除，不用擔心會弄亂系統」**現在是錯的，而且權限已經開了**。
每多一天，就多一天有人照著它做。
三條是：這張表直接連網站、只有 `Approved` 會上線、一列填錯全體停擺。

**02　口頭強調兩條機器擋不住的規則**
「不要刪整列」和「已核可的列不要直接改」。
這兩條目前沒有任何程式防線，只能靠人守。
明說它們是暫時的權宜，做好之後會取消。講明是權宜，比假裝是制度好。

**03　把會議用在「只有學者能回答的三題」上**
這三題回答完就能立刻解掉三張卡住的票。見下一節。

**04　手動加上 `approved_by`、`approved_at`、`reject_reason` 三欄**
同步程式已經支援這三欄，加上不會壞。
加了之後，核可和退稿才留得下紀錄。學者也才有地方看到退稿原因。
目前退稿沒有任何地方寫原因。
