## ⚠️ 修正補述（2026-08-31，同日稍晚）

**本報告內文多處以「網站正在對外散布錯誤內容」描述問題的嚴重性。該前提未經查證，事後確認為不精確。**

經確認的實際狀況：

- 網站**有連結才看得到**，目前受眾為工作夥伴，其中包含法學背景者
- `LaunchGate` 的 `NEXT_PUBLIC_PUBLIC_MODE` 未設定，因此所有頁面對持有連結者開放。該 gate 只有「全開」與「僅開放 `/`、`/controversy-timeline`、`/future` 三頁」兩種狀態，無法做到「夥伴看全部、公眾看部分」
- `LaunchGate` 為 client-side 判斷（localStorage），頁面仍完整送達瀏覽器，屬視覺遮蔽而非存取控制
- 查證時發現：專案**無 `robots.txt`、無 `noindex` 設定**，且 metadata 含完整 OpenGraph 與 Twitter card。「不會被 Google 查到」當時僅成立於「尚無人公開張貼連結」，非設定所致。已於同日加入 `robots: { index: false, follow: false }` 並驗證產生的 HTML 確實輸出該標籤

**據此調整的判斷：**

| 項目              | 原判斷        | 修正後                                            |
| --------------- | ---------- | ---------------------------------------------- |
| 佔位摘要、測試字串       | 對外出錯，最高優先  | 上線前必須清乾淨，非立即傷害                                 |
| `h2` 釋字272 法律錯誤 | 對外散布錯誤法律內容 | **維持高優先**，但理由改變 —— 看到它的人包含法學者，專案信任的損害比公開與否更難補救 |
| 資料損壞本身（15 筆錯位）  | —          | 判斷不變。與受眾無關，是資料正確性問題                            |

**保留原始判斷不刪除的理由**：判斷是在什麼證據基礎上做出的、後來如何被修正，本身就是這份記錄的價值。把錯誤的前提悄悄改掉，會讓文件看起來一直都對，反而失去參考意義。

## ⚠️ 第二次補述（2026-09-01）—— 找到了壞資料的「送達機制」

**本報告的「三、根因」只解釋了資料為什麼會壞，沒有解釋它為什麼會上線。**

體檢當時留下一個未解的疑問：沒有人手動跑同步，壞資料是怎麼抵達線上的？答案在 `package.json`：

```json
"build": "node scripts/sync-content.mjs && next build"
```

**每次部署都會重新抓一次試算表。** 只要有人推 code 觸發部署，同步就跑一次 —— 不需要任何人手動操作，壞資料自己上線，而且沒有人看過改了什麼。

這是原報告缺的那一塊：根因（人工複製壞掉）解釋了資料**為什麼壞**，這個機制解釋了它**為什麼會在無人操作的情況下對外顯示**。

### 三個破洞

| | 破洞 | 造成什麼 |
|---|---|---|
| 1 | **部署會自動同步** | 壞資料不需要任何人動手就會上線，且無人看過 diff |
| 2 | **系統從未拒絕過任何資料** | 遇到問題只印一行警告然後繼續跑完。那 15 筆每一筆都違反基本規則（年份欄裡是整段憲法條文），全數放行 |
| 3 | **核可的人看不到成品** | 編輯台只看得到試算表的格子。`test test test` 在格子裡只是一串字，在網站上是一個對外顯示的區塊 |

### 四道防線

| | 防線 | 擋掉哪個破洞 | 對應施工項目 |
|---|---|---|---|
| 1 | 部署不准執行同步 | 破洞 1 | `design.md` 第七節第 8 項 |
| 2 | 資料有問題就整份停下，一個檔案都不寫 | 破洞 2 | `design.md` 第四節、第七節第 7 項 |
| 3 | 只收 `status = Approved`，空白不算通過 | 發現 4（Track 1 完全沒把關） | `design.md` 第三節、第七節第 7 項 |
| 4 | 每次同步開 PR，用 diff 與預覽網址審 | 破洞 3 | `design.md` 第五節、第七節第 9 項 |

**為什麼防線 2 是「整份停下」而不是「跳過壞的那幾筆」**：跳過會讓資料悄悄變少而無人察覺，那只是換一種形式的靜默失敗。詳見 `design.md` 第四節。

**防線 3 現在有一個實際受益者**：`h2`（釋字第 272 號）在試算表裡的 `status` 是空白的。改成嚴格模式後，空白就等於擋住 —— 正好把那筆擋著，等法學的人確認完再放行。目前的寬鬆模式擋不住它，見 `TODO.md` 的 P2-1。

### 這次體檢真正的教訓

三次事故 —— 15 筆欄位錯位、測試字串上線、寫好的摘要被覆蓋 —— 表面原因各不相同，但**共同模式只有一個**：

> **不該發生的事情發生了，而且沒有發出任何聲音。**

2026-09-01 又發現兩件同型的：

- `d1` 的反方意見掛著虛構出處（`某學者，某大學法律系`），正在線上顯示。來源是把設計文件裡標題為「Sample data shape」的**結構示範**，當成真實內容寫進了資料檔。見 `TODO.md` 的 P0-5
- 新建的 `site_tldr` 分頁若不處理，會讓網站的 TL;DR 區塊在產線接通後**無聲消失** —— 不報錯、不擋建置。見 `TODO.md` 的 P1-5

**所以四道防線的共同目的不是「防止出錯」，而是「出錯時會停下來講話」。** 人一定會犯錯，試算表一定會被貼歪，示範資料一定會有人誤當成內容 —— 差別只在於系統會不會告訴你。

## 摘要

原本的問題是「三個資料夾如何整理，以利多人協作」。體檢後發現，資料夾的混亂是**症狀**而非病因。

真正的狀況是：**一條餵養網站的內容產線，中間有一個由人工複製構成的環節，而該環節同時扮演「編輯把關」與「資料搬運」兩種角色。它把搬運做壞了，且把關只做了一半。**

三份資料重複、`_備份` 檔名、兩張同名 SSOT —— 都是這條產線缺乏定義所產生的結果。直接整理資料夾，症狀會再長回來。

**最嚴重的三項發現：**

1. 網站 Track 1 的 25 筆資料中，**15 筆（60%）欄位錯位**，年份欄顯示整段憲法條文
2. 網站正在顯示一筆**法律內容錯誤**的資料（釋字第272號），而正確版本早已存在於上游試算表，只是沒有回流
3. 機器產生的資料檔已被人工編輯，**執行既有的同步指令會使網站倒退**

## 一、產線構造

```
        寫作者（法學者・編輯・允鍾）
                 ↓ 編輯
        ┌──────────────────────┐
        │ SSOT_收集區            │  Track 1: 42 列　Track 2: 44 列
        │ Google Drive          │  含專家改正・欄位標題帶註解
        └──────────────────────┘
                 ↓ ✋ 人工複製
                   （無人負責・會貼歪・不回流）
        ┌──────────────────────┐
        │ SSOT_Editor           │  Track 1: 25 列　Track 2: 17 列
        │ Google Drive          │  15 筆錯位・含法律錯誤・含 test 資料
        └──────────────────────┘
                 ↓ node scripts/sync-content.mjs
                   （依欄位「標題名稱」對應，非位置）
        ┌──────────────────────┐
        │ src/data/history.json      25 筆
        │ src/data/discussions.json  16 筆・已被人工編輯
        └──────────────────────┘
                 ↓ Next.js
              線上網站
```

### 設計意圖是正確的

`SSOT_收集區` 的「使用說明」分頁記載了原始設計：

> 1. 此檔案僅為資料人工收集區：會再複製到給機器讀取的文件，此處可自由編輯刪除，不用擔心會弄亂系統
> 2. Track 1, Track 2 編輯通則：粉紅底色欄位：必填／黃底色欄位：選填／其他未標色欄位：次選填（可AI生成後再校對）
> 3. Track 1 資料是我從黑客松活動整理的部分資料丟入，若有錯誤請直接改正
> 4. Track 2 中，希望置頂的請在 "sticky" 一欄勾選 "TRUE"

意圖清楚：`收集區` 是多人自由投稿區，`Editor` 是編輯台，兩者分離是為了讓投稿區可以被弄亂而不影響生產資料。**這個設計本身沒有問題，壞的是它的實作。**

## 二、發現

### 發現 1：人工複製造成 60% 的資料損壞

**現象**：`history.json` 25 筆中 15 筆結構損壞。

```
h15  chapter: "1998"                              ← 應為 year
     content: "釋字第445號"                        ← 應為 ruling_id
     year:    "憲法第十四條規定人民有集會之自由…"      ← 應為 content
     ruling_id: ""                                ← 空白
```

**規律**：`h1`–`h14` 全部正常，`h15`–`h29` 全部損壞。

**機制**：兩張表的欄位順序不同。

```
收集區  Track 1:  id, category, year, ruling_id, ruling, content, handwriting, title, image_url        （9 欄）
Editor Track 1:  id, category, chapter, content, handwriting, year, title, ruling, ruling_id, image_url （10 欄，多 chapter）
```

將 `收集區` 的列直接貼入 `Editor` 而未重新對應欄位，即產生固定的位移：

| 收集區 | → Editor |
|---|---|
| `year` | `chapter` |
| `ruling_id` | `content` |
| `ruling` | `handwriting` |
| `content` | `year` |
| — | `ruling_id` 留空 |

**推論**：這是單次批次操作的結果，不是逐列手誤累積。

**受影響**：`h15` `h16` `h17` `h18` `h19` `h20` `h21` `h22` `h23` `h24` `h25` `h26` `h27` `h28` `h29`

### 發現 2：`收集區` 才是內容真相，`Editor` 又舊又錯

一般會假設「編輯台的版本比較新、比較乾淨」。實際相反。

**證據 A — 法律內容錯誤未回流**

| | 線上（來自 Editor） | 收集區（已改正） |
|---|---|---|
| category | 言論自由 | **訴訟權** |
| ruling | 廢除刑法100條運動・保障和平表達政治異議的自由 | 限制戒嚴時已確定之軍事審判案件只能透過再審或非常上訴途徑救濟，並不違憲 |
| content | 憲法第十一條規定人民有言論、講學、著作及出版之自由… | 戒嚴期間非現役軍人受軍事審判，屬憲法容許之例外… |

釋字第272號為軍事審判案件，非言論自由案件。有人在 `收集區` 依「若有錯誤請直接改正」的指示改對了，但該修正**永遠停在 `收集區`**，因為回流路徑不存在。

此列結構正常，機械掃描偵測不到 —— 只有人讀才會發現。這代表**同類錯誤可能還有，且無法自動找出**。

**證據 B — 資料量落差**

| | 收集區 | Editor | 線上 |
|---|---|---|---|
| Track 1 | 42 列 | 25 列 | 25 筆 |
| Track 2 | 44 列 | 17 列 | 16 筆 |

**證據 C — 內容完整度**

| 項目 | 收集區 | Editor |
|---|---|---|
| `d2` 摘要 | 真摘要（英文原文） | 佔位文字 |
| `d3`（郭銘松 Part II） | 完整內容 | `status` 空白 → 未上線 |
| `d18` | 有 | 無 |
| `h22` 之後 | 有 | 部分缺 |

**結論**：`Editor` 是 `收集區` 的一份劣化副本。sync 讀的是劣化的那一份。

**來源確認方式**：`history.json` 為 25 筆，與 `Editor` 的 25 列吻合（`收集區` 為 42 列）；且 `history.json` 的錯位樣態與 `Editor` 完全一致。`.env.local` 中的網址為 Google「發布到網路」的匿名 CSV 網址，無法從網址本身辨識 sheet，故以內容比對確認，非以網址推定。

### 發現 3：機器產出的檔案已被人工編輯

**現象**：`discussions.json` 中存在試算表裡不存在的內容。

```
線上 d1 短評：「憲法法庭沒死，只是被鎖在抽屜裡——這篇說的是誰把鑰匙拿回來了。」
Editor d1 短評：「這篇太長，我看完了：大法官說快來開會啦！」   ← 佔位
收集區 d1 短評：「長期關心司法議題的張娟芬老師寫給非法律人的你瞭解！」
```

三個版本，三個地方，互不相同。

**盤點結果**（詳見 `docs/content-rescue/track2-rescue.md`）：

| 類別 | 筆數 | id | 說明 |
|---|---|---|---|
| A 孤兒 | 3 | `d7` `d8` `d9` | 試算表為空，json 是唯一版本 |
| B 兩版並存 | 5 | `d1` `d2` `d4` `d5` `d6` | 兩邊都是真短評，風格不同 |
| C 一致 | 7 | `d11`–`d17` | 安全 |

B 類是意外發現：原以為試算表側是佔位文字，實際上兩套都是認真寫的短評，只是**聲音不同** —— json 版口語、有個性；試算表版偏說明性導讀。這不是資料錯誤，是**尚未做出的編輯決定**。

**同時發現兩項僅存於 json 的資產**：

1. **`vibe` 的第二套分類**：`🔥 公民必讀` `🌍 國際視角` `💬 正反交鋒` `📖 深度解析` `📣 懶人入門` —— 這 5 個在兩張試算表中皆不存在。`d1`–`d9` 使用新分類，`d11`–`d17` 使用舊分類。判讀為：有人設計了更細緻的分類，但只套用了一半。

2. **`opposing_views`（正反交鋒）**：僅 `d1` 一筆，2 個觀點，1,010 字元。為巢狀結構（`stanceLabel` / `summary` / `fullArgument` / `source{}` / `editorialNote` / `editorialSources[]`），平面試算表無法容納。由 `src/app/present/[id]/page.tsx` 與 `src/components/SharedPresent.tsx` 渲染，屬線上功能。**`sync-content.mjs` 的輸出欄位中沒有此欄。**

**風險**：執行 `node scripts/sync-content.mjs` 會以試算表的佔位值覆蓋線上較好的短評，並完全抹除 `opposing_views`。

**成因**：這是「機器讀的檔案不得手改」這條規則被打破的結果。諷刺的是，被手改的那份現在是品質最好的版本 —— 因為人在最接近成品的地方修東西，總是比繞回上游容易。

**時效**：`discussions.json` 最後 commit 於 2026-05-02，距今近 4 個月。

### 發現 4：編輯台的把關只做了一半

`scripts/sync-content.mjs` 中，兩軌的過濾條件不同：

```js
// Track 1 — 無把關
.filter(row => !row.status || row.status.toLowerCase() === 'approved')

// Track 2 — 有把關
.filter(row => row.status && row.status.toLowerCase() === 'approved')
```

`Editor` 的 Track 1 **沒有 `status` 欄位**，因此 `!row.status` 恆為真 —— 每一列無條件放行。

**這解釋了發現 1**：那 15 筆壞資料之所以能上線，是因為 Track 1 的唯一關卡就是「有人把它複製過來」這個動作本身。而同一個動作既是閘門也是污染源 —— **通過閘門的方式，就是弄壞資料的方式**。

Track 2 有 `status` 過濾，但也不足以信任：`tldr` 該列的 `abstract` 為 `**權限界線**：test test test test…`，`status` 卻標為 `Approved`，因此正在對外顯示。

**判讀**：把關機制存在於設計中，但不存在於執行中。

## 三、根因

> ⚠️ **本節不完整，請併同文件上方的「第二次補述（2026-09-01）」閱讀。**
> 本節解釋了資料**為什麼會壞**，但沒有解釋它**為什麼會上線** —— 送達機制是「每次部署都會自動重跑同步」，該事實於體檢後才查出。

四項發現指向同一個結構問題：

> **人工複製這個動作，同時承擔了「編輯把關」與「資料搬運」兩個職責。**

- 作為**搬運**：因兩表欄位順序不同而系統性貼歪（發現 1），且單向不可逆，上游修正無法回流（發現 2）
- 作為**把關**：Track 1 因缺 `status` 欄而完全失效，「被複製過來」等於「通過審核」（發現 4）
- 因為這個環節不可靠，人們繞過它 —— 直接改機器產出的檔案（發現 3），或另存備份（發現 6）

資料夾的混亂由此而來，而非相反。

**一項重要的釐清**：初步建議曾提出「合併兩張表、廢除中間層」。經確認編輯台的職責後，此建議需修正 —— 中間層承載的**把關功能必須保留**，該廢除的只是「以複製作為把關手段」這個實作方式。

由於編輯台的角色是「只核可，不改內容」，把關可改以**欄位**實現而非**檔案搬運**：單一表格 + `status` 欄 + Google 試算表「保護範圍」限制編輯者。如此把關權力不減反增（Track 1 首次具備閘門），同時消除搬運錯誤的發生條件。
