## 要解決什麼問題

2026 年 8 月發現三件事：

1. 網站上 25 筆歷史資料中，有 15 筆的欄位錯位。年份欄裡是一整段憲法條文。
2. 一筆法律內容錯誤。釋字第 272 號被寫成言論自由案，實際是軍事審判案。
3. 測試字串 `test test test` 對外顯示。

**根本原因**：中間有一個「人工複製」的動作，同時做兩件事 —— 編輯把關，以及資料搬運。
它把搬運做壞了，把關也只做了一半。

**新流程保留把關，移除人工搬運，並補上系統從來沒有的能力：拒絕不合格的資料。**

## 一、唯一真相是哪張表

**只留一張表：`SSOT_收集區`（改名為 `SSOT`）。另一張 `SSOT_Editor` 封存。**

為什麼選它，2026-08-31 實測：

| | `SSOT_收集區` | `SSOT_Editor` |
|---|---|---|
| 歷史軌筆數 | 42 | 25 |
| 討論軌筆數 | 44 | 17 |
| `h2` 的法律錯誤 | 已改正 | 仍是錯的 |
| `h23`／`h24` 的敘述 | 已重寫得更精確 | 舊版，含錯字 |
| 欄位錯位 | 無 | 15 筆 |

`SSOT_Editor` 從頭到尾都是 `收集區` 的劣化副本。

> **「唯一真相」是什麼意思**：同一份內容只能有一個來源。
> 有兩個來源時，兩邊會各自被修改，然後沒有人知道哪邊才對。
> 這正是 `h2` 的法律錯誤在 `收集區` 被改正後，四個月都沒有反映到網站的原因。

|---|---|

| `Track 1_history` | 歷史軌內容 |

> 詳見文末修訂紀錄。

### 欄位標題可以保留中文說明

**標題寫成這樣沒有問題：**

```
✓  id (給系統看的編號)
✓  content （現有為AI生成）
✓  owl comment (允鍾如果有靈感可以寫一句短評)
```

那些中文是寫給學者老師看的，是他們編輯時唯一的欄位指引。刪掉他們就不知道該填什麼。

**同步程式會自己看懂。** 做法是「最長前綴比對」：

1. 把標題去掉頭尾空白、轉小寫
2. 在預期的欄位清單裡，找出「標題等於它」或「標題以它加分隔符開頭」的候選
3. **取最長的那個**（所以 `owl comment` 不會被誤認成 `owl`）
4. **找不到就中止，並指名是哪個標題看不懂**

第 4 點才是重點。前三點只是方便。**關鍵是看不懂的時候要大聲停下，不是默默把整欄變成空白。**

**已實測**（2026-09-01，用現行程式裡真正的 `parseCSV`，不是另外寫一個）：

| 輸入 | 結果 |
|---|---|
| Track 1 全部 10 個真實標題 | ✅ 全數正確 |
| Track 2 全部 12 個真實標題 | ✅ 全數正確 |
| `id 給系統看的編號`（沒有括號） | ✅ → `id` |
| `content - 現有為AI生成` | ✅ → `content` |
| `title [AI生成]` / `Status`（大小寫） | ✅ → `title` / `status` |
| `owl comment (允鍾…)` | ✅ → `owl comment`，沒有誤判成 `owl` |
| `ruling_di (判解字號)`（真的打錯字） | ⛔ 看不懂 → 中止並指名 |

### `Track 1_history` 的欄位

| 欄位 | 必填 | 誰可以改 |
|---|---|---|
| `id` `category` `year` `ruling_id` `ruling` `content` `title` | ✓ | 投稿者 |
| `handwriting` `image_url` | | 投稿者 |
| **`status`** | ✓ | **只有編輯台**（設保護範圍） |
| `approved_by` `approved_at` `reject_reason` | | 只有編輯台 |

`status` 是新增的欄位。**原本沒有這一欄，導致每一列都無條件放行** —— 這是 15 筆壞資料能上線的直接原因。

### `Track 2_discussion` 的欄位

沿用現有欄位。`status` 改為保護範圍，`vibe` 改為下拉選單。

| 欄位 | 必填 | 誰可以改 |
|---|---|---|
| `id` `category` `title` `author` `year` `link` `abstract` | ✓ | 投稿者 |
| `owl comment` `views` `sticky` | | 投稿者 |
| `vibe` | ✓ | 投稿者（限下拉選項） |
| **`status`** `approved_by` `approved_at` `reject_reason` | ✓ | **只有編輯台** |

### `site_tldr` 的欄位（新增分頁）

`tldr` 原本是 `Track 2_discussion` 的一列。**但它不是一篇討論** —— 沒有作者、沒有年份、沒有語氣標籤。它是網站上的一個版面元件。

**留在 Track 2 會讓檢查機制擋下整份同步。** Track 2 的 `year` 與 `vibe` 是必填，而 tldr 兩者都空。
配上「檢查失敗就整份停下」，照舊設計做完，第一次跑同步就會被自己擋住。

**解法：獨立分頁，一列一個重點。**

| 欄位 | 必填 | 說明 |
|---|---|---|
| `order` | ✓ | 排序。`0` 是標題列，`1` 起是內容重點 |
| `label` | ✓ | 重點小標，例如「權限界線」 |
| `text` | ✓ | 重點內文。`order 0` 時是網站顯示的標題 |
| `status` | ✓ | 只有編輯台（設保護範圍） |
| `link` | | 只有 `order 0` 用，摘要的出處連結 |

**同步程式要怎麼把它組回網站要的格式：**

1. 取 `status = Approved` 的列，依 `order` 排序
2. `order 0` → 這筆的 `title` 與 `link`
3. `order ≥ 1` → 各列組成 `**{label}**：{text}`，用換行接起來
4. 產出一筆 `id: 'tldr'`、`category: 'Official TL;DR'`、`author: '憲庭加好友'`

**環境變數**：`SITE_TLDR_CSV_URL`（新增）

> ⚠️ **發布網址的值不寫進 repo。** 那個網址等於整份試算表的公開讀取入口。
> 寫進版控就是把試算表跟著 repo 一起公開。只記變數名稱。

> ⚠️ **`order 0` 那列的 `status` 必須是 `Approved`。**
> 只收 `Approved` 的話，空白會讓標題和連結被濾掉，摘要區塊會變成沒有抬頭、點不出去。

> ⚠️ **`id: 'tldr'` 這個值不可以改。**
> 網站用 `DISCUSSIONS_DATA.find(item => item.id === 'tldr')` 找它（`src/app/present/page.tsx:392`）。
> 而 `OfficialTLDR` 的第一行是 `if (!item) return null`（同檔 L75）——
> **找不到不會報錯、不會擋建置，整個區塊直接消失。**

## 三、誰來把關

**編輯台的職責是「只核可，不改內容」。所以把關用欄位做，不用檔案搬運做。**

```
投稿者：可以編輯所有內容欄位，但 status 欄鎖住，改不到
編輯台：唯一能把 status 改成 Approved 的人
同步  ：只收 status = Approved 的列
```

用 Google 試算表的「保護範圍」功能限制 `status` 欄的編輯權限。

**和舊做法比較：**

| | 舊：用複製當閘門 | 新：用 status 當閘門 |
|---|---|---|
| 有沒有把關 | ✓ | ✓ |
| 歷史軌是否真的有把關 | ✗ 完全沒有 | ✓ |
| 會不會貼歪欄位 | ✗ 已發生 15 筆 | 資料不移動，不可能 |
| 上游修正能不能回流 | ✗ `h2` 卡了四個月 | 同一列，自動 |
| 有沒有核可紀錄 | 無 | `approved_by`／`approved_at` |
| 有沒有退稿機制 | 無 | `status = Rejected` ＋ 退稿原因 |

**編輯台的權力沒有變少。只是換了做法，而且管得更多。**

## 四、檢查機制

> 這是本次唯一新增的常設檢查，已於 2026-08-31 取得明確核可。

### 為什麼需要

現行同步程式遇到問題只印一行警告，然後繼續跑完。**系統從來沒有拒絕過任何資料。**

那 15 筆壞資料，每一筆都違反下面前兩條規則。當時如果有這個機制，一筆都上不了線。

### 檢查什麼

**共通**

- 每個欄位標題都必須能對應到預期欄位，否則中止並指名
- `id` 不可空白、不可重複（`site_tldr` 以 `order` 為鍵，同一規則）
- 標記必填的欄位不可空白
- `status` 必須是 `Approved`／`Rejected`／空白其中之一
- **欄位標題不可重複** —— 程式以標題字串為鍵，重複時後者會覆蓋前者，前者的內容會無聲消失

**Track 1**

- `year` 必須是 4 位數字
- `ruling_id` 不可空白
- `image_url` 若非空，必須是合法網址

**Track 2**

- `link` 必須是合法網址
- `vibe` 必須在允許清單內
- `abstract` 不可含 `test test`、`lorem ipsum` 等測試字樣
- `sticky` 必須是 `TRUE`／`FALSE`／空白

**site_tldr**

- `order` 必須是非負整數，且不可重複
- 必須有 `order 0` 的列，**且它的 `status` 是 `Approved`**
- `order 0` 的 `link` 必須是合法網址
- `order ≥ 1` 至少要有一列通過核可
- `text` 不可含測試字樣

### 檢查失敗時怎麼辦

**整份停下，一個檔案都不寫。**

```
🚀 Starting Content Sync...
❌ 驗證失敗，未寫入任何檔案：

  Track 1
    h15  year 應為 4 位數字，實際為「憲法第十四條規定人民有集會之自由…」
    h15  ruling_id 不可為空
  site_tldr
    order 1  text 含有測試字串「test test test」

共 3 項錯誤。請修正 SSOT 後重試。
```

**設計要點：全有全無。**

不可以「跳過壞的列、寫入好的列」。那會讓資料悄悄變少而沒有人察覺 —— 只是換一種形式的靜默失敗。

## 五、更新流程與施工順序

### 內容更新流程（做完之後長這樣）

```
①  寫作者（法學者・編輯）
    │
    │  在試算表填內容。status 欄改不到。
    ▼
   ┌──────────────────────────────────┐
   │  SSOT 試算表  ← 唯一真相           │
   │                                  │
   │   Track 1_history    歷史軌       │
   │   Track 2_discussion 討論軌       │
   │   site_tldr          網站摘要區塊  │
   └──────────────────────────────────┘
    │
    ▼
②  編輯台核可
    │
    │  把 status 改成 Approved。只有編輯台能改這一欄。
    │  退稿就改成 Rejected，並填退稿原因。
    ▼
③  工程師手動執行同步     ← 重點：不是自動，要有人按
    │
    ├─── 檢查資料 ──── 有問題？
    │                   │
    │                   ▼
    │              整份停下。一個檔案都不寫。
    │              列出是哪幾筆、哪一欄、錯在哪。
    │
    ▼ 全部通過才繼續
   src/data/*.json
    │
    ▼
④  開 PR
    │
    ├─ diff  ＝ 這次要發布什麼的完整清單，逐字可看
    └─ Vercel 自動產生預覽網址 ← 編輯台在這裡看實際畫面
    │
    ▼  有人看過並同意
⑤  合併 → 部署
    部署只讀已存檔的資料，不再抓試算表。
```

**預覽用 PR 的預覽網址，不另外架 staging 環境。**

理由：staging 的用途是給不會用 GitHub 的人一個固定網址。現在的編輯台決策者可以直接用 GitHub。
而且 PR 預覽顯示的是「這次要發布的內容」，跟核可決策的對象完全一致；
staging 顯示的是「目前所有已核可內容」，那是另一個問題。

這一步補上系統原本缺的一環：**核可的人看得到成品。**
測試字串和佔位摘要之所以能上線，就是因為核可者只看得到試算表格子。

## 六、不變式

**以下規則不可違反。違反任何一條，本次事故會以某種形式重演。**

| # | 規則 | 對應的失敗 |
|---|---|---|
| 1 | **部署不可執行同步** | 原本 `build = sync && next build`，每次部署都靜默重抓資料，沒有人看過 diff |
| 2 | **`src/data/*.json` 是產物，不可手改** | `discussions.json` 被手改，導致「跑同步會讓網站倒退」 |
| 3 | **檢查失敗即中止，不可部分寫入** | 現行只印警告後繼續，等於沒有把關 |
| 4 | **只能有一份唯一真相** | 兩份真相導致修正無法回流、資料反向覆蓋 |
| 5 | **欄位標題必須能對應到預期欄位，否則中止** | 同步以標題字串取值，取不到則整欄靜默變空。2026-09-01 修訂，原為「標題不得帶註解」 |
| 6 | **約定必須可被機器驗證** | 「粉紅底色＝必填」機器讀不到，無法強制執行 |

> **第 6 條是最容易被違反的一條。**

### 2026-09-01 — 推翻「欄位標題不得帶註解」

**captain 的反對**：那些中文說明（`id (給系統看的編號)` 等）是寫給學者老師看的。
