## 這份文件要解決什麼

原本的產線在 2026-08 發生事故：Track 1 的 25 筆資料中 15 筆欄位錯位、一筆法律內容錯誤、測試字串對外顯示。詳細成因見背景診斷。

根因是：**人工複製這個動作同時承擔「編輯把關」與「資料搬運」兩個職責**，而它把搬運做壞了，把關也只做了一半。

本設計保留把關、移除人工搬運，並補上系統從未有過的東西 —— **拒絕不合格資料的能力**。

## 二、試算表結構

### 分頁

| 分頁 | 用途 |
|---|---|
| `使用說明` | 給人看的編輯規則 |
| `Track 1_history` | 歷史軌內容 |
| `Track 2_discussion` | 討論軌內容 |
| `Track 2_opposing` | **新增**，正反交鋒觀點 |
| `site_tldr` | **新增**，網站置頂的 TL;DR 版面元件（非討論內容） |

### 欄位標題規則

**標題可以保留中文說明。由程式負責對應，不要求人去遷就機器。**

```
✓  id (給系統看的編號)
✓  content （現有為AI生成）
✓  owl comment (允鍾如果有靈感可以寫一句短評)
```

**原設計要求「標題必須乾淨、不得帶註解」，2026-09-01 推翻。** 理由：那些中文說明是寫給學者老師看的，是他們在編輯時唯一的欄位指引；刪掉會讓編輯端失去判斷依據。而且「大家記得不要在標題加註解」是一條**沒有人在看的人為約定** —— 違反不變式 #6（約定必須可被機器驗證）。哪天有人手滑加回去，該欄會靜默全空。

**改為：最長前綴比對。** 預期欄位表是已知的，因此不需要猜註解從哪裡開始 ——

1. 標題去頭尾空白、轉小寫、連續空白收斂為一個
2. 在預期欄位表中找出所有「標題等於它，或標題以它加分隔符開頭」的候選（分隔符：半形／全形空格、`(`、`（`、`[`、`-`、`－`）
3. **取最長的那個**（`owl comment` 因此不會被誤判為 `owl`）
4. **找不到 → 中止，並指名是哪個標題無法辨識**

第 4 點才是真正的保證。前三點只是便利 —— 重點是解析不出來時**大聲停下**，而不是靜默產生一個空欄位。

**已實測**（2026-09-01，以現行 `parseCSV` 與真實標題驗證）：

| 輸入 | 結果 |
|---|---|
| Track 1 全部 10 個真實標題 | ✅ 全數正確對應 |
| Track 2 全部 12 個真實標題 | ✅ 全數正確對應 |
| `id 給系統看的編號`（無括號） | ✅ → `id` |
| `content - 現有為AI生成` | ✅ → `content` |
| `title [AI生成]` / `Status`（大小寫） | ✅ → `title` / `status` |
| `owl comment (允鍾…)` | ✅ → `owl comment`，未誤判為 `owl` |
| `ruling_di (判解字號)`（真的打錯字） | ⛔ 無法辨識 → 中止並指名 |

`status` 為新增欄位。原本 Track 1 沒有此欄，導致 sync 的過濾條件 `!row.status || approved` 恆為真，**每一列無條件放行** —— 這是 15 筆壞資料能上線的直接原因。

### Track 2_discussion

沿用現有欄位，`status` 改為保護範圍，`vibe` 改為下拉選單。

| 欄位 | 必填 | 誰可編輯 |
|---|---|---|

| **`status`** `approved_by` `approved_at` `reject_reason` | ✓ | **僅編輯台** |

### Track 2_opposing（新增）

`opposing_views` 為巢狀結構（一篇文章 → 多個觀點 → 每個觀點含多個欄位與多條連結），平面試算表無法直接容納。

**解法：攤平。一列代表一個觀點，以 `discussion_id` 標明歸屬，sync 讀取時依此分組還原為巢狀。**

| 欄位 | 說明 |
|---|---|
| `discussion_id` | 對應 Track 2 的 `id`，例如 `d1` |
| `stance_label` | 立場標籤 |
| `summary` | 簡述 |
| `full_argument` | 完整論證 |
| `source_author` `source_affiliation` `source_year` | 出處 |
| `editorial_note` | 編輯按語 |
| `source_label_1` `source_url_1` | 參考連結（如需更多，增列欄位對） |
| `status` | 僅編輯台 |

此變更同時解決一個既有問題：`opposing_views` 目前只存在於 `discussions.json`，**編輯台完全看不到它**，其中的佔位出處（`某學者` / `某大學法律系`）正在對外顯示而無人能察覺。攤平後它與其他內容受同一套把關。

### site_tldr（新增）

`tldr` 原本是 `Track 2_discussion` 的一列，但**它不是一篇討論** —— 沒有作者、沒有年份、沒有 `vibe`。它是 `/present` 頁面上的一個版面元件。

**把它留在 Track 2 會讓第四節的驗證器中止整份 sync。** Track 2 的 `year` 與 `vibe` 為必填（見上表），而 tldr 這筆兩者皆空；第四節的行為是「驗證失敗即中止，不寫入任何檔案」且「全有全無」。這不是假設 —— 是照本設計做完施工項目 7 之後，第一次跑 sync 就會發生的事。

**解法：獨立分頁，一列一重點。** 與 `Track 2_opposing` 同一路數 —— 網站上是多段結構的東西，在試算表裡攤平成列。

| 欄位 | 必填 | 說明 |
|---|---|---|
| `order` | ✓ | 排序鍵，取代 `id`。`0` 為標題列，`1` 起為內容重點 |
| `label` | ✓ | 重點小標，如「權限界線」；`order 0` 時為 `標題與連結` |
| `text` | ✓ | 重點內文；`order 0` 時為網站顯示的標題 |
| `status` | ✓ | 僅編輯台（保護範圍） |
| `link` | | 僅 `order 0` 使用，TL;DR 的出處連結 |

**sync 還原方式**（施工項目 7）：

- 取 `status = Approved` 的列，依 `order` 排序
- `order 0` → 該筆的 `title` 與 `link`
- `order ≥ 1` → 各列組成 `**{label}**：{text}`，以換行接起成為 `abstract`
- 產出一筆 `id: 'tldr'`、`category: 'Official TL;DR'`、`author: '憲庭加好友'` 併入 `discussions.json`

**環境變數**：`SITE_TLDR_CSV_URL`（新增，與 `TRACK_1_CSV_URL` / `TRACK_2_CSV_URL` 同一機制）。

> ⚠️ **發布網址的值不記錄於本 repo。** 該網址是整份 SSOT 的公開讀取入口，寫進版控等同於把試算表跟著 repo 一併公開。沿用 TODO P2-5 的既有慣例：只記變數名，值放環境變數，並於 `.env.example` 記錄取得方式。

⚠️ **`order 0` 那列的 `status` 也必須是 `Approved`。** 目前是空白 —— 若照把關機制只收 `Approved`，標題與連結會被靜默濾掉，TL;DR 會變成一個沒有抬頭、點不出去的區塊。這是本分頁最容易犯的錯，故列為驗證規則（見第四節）。

⚠️ **`id: 'tldr'` 這個值不可更動。** 網站以 `DISCUSSIONS_DATA.find(item => item.id === 'tldr')` 取用（`src/app/present/page.tsx:392`），而 `OfficialTLDR` 的第一行是 `if (!item) return null`（同檔 L75）—— 取不到不報錯、不擋 build，整個區塊直接消失。這是不變式 #3 所防的靜默失敗在**渲染層**的同型風險，故在此明文標註。

## 三、把關機制

**編輯台的職責是「只核可，不改內容」。** 因此把關以**欄位**實現，而非檔案搬運。

```
投稿者：可編輯所有內容欄位，但 status 欄鎖住，改不到
編輯台：唯一能把 status 改成 Approved 的人
sync  ：只收 status = Approved 的列
```

以 Google 試算表的「保護範圍」功能限制 `status` 欄的編輯權限。

**與原機制的比較：**

| | 原：複製當閘門 | 新：status 當閘門 |
|---|---|---|
| 把關 | ✓ | ✓ |
| Track 1 是否真的有把關 | ✗ 完全沒有 | ✓ |
| 會否貼歪欄位 | ✗ 已發生 15 筆 | 資料不移動，不可能 |
| 上游修正能否回流 | ✗ h2 卡住至今 | 同一列，自動 |
| 核可紀錄 | 無 | `approved_by` / `approved_at` |
| 退稿機制 | 無 | `status = Rejected` + `reject_reason` |

**編輯台的權力沒有變少，只是換了實現方式，且涵蓋範圍變大。**

## 四、驗證機制

> 本節為本次新增的常設檢查，已於 2026-08-31 取得明確核可。

### 為什麼需要

現行 sync 遇到問題只印警告後繼續執行。**系統從未拒絕過任何資料。** 那 15 筆壞資料每一筆都違反下列前兩條規則，若當時有此機制即無法上線。

### 規則

**共通**
- **每個欄位標題都必須能解析到預期欄位**，否則中止並指名（見第二節「欄位標題規則」）
- `id` 不得為空、不得重複（`site_tldr` 以 `order` 為鍵，適用同一規則）
- 標記必填的欄位不得為空
- `status` 必須是 `Approved` / `Rejected` / 空白之一
- **欄位標題不得重複** —— `parseCSV` 以標題字串為 key，重複時後者會覆蓋前者。兩欄同名而值不同時，前者的內容會無聲消失

**Track 1**
- `year` 必須為 4 位數字
- `ruling_id` 不得為空
- `image_url` 若非空，必須是合法網址

**Track 2**
- `link` 必須是合法網址
- `vibe` 必須在允許清單內
- `abstract` 不得含 `test test`、`lorem ipsum` 等測試字樣
- `sticky` 必須是 `TRUE` / `FALSE` / 空白

**Track 2_opposing**
- `discussion_id` 必須對應到 Track 2 中實際存在的 `id`

**site_tldr**
- `order` 必須為非負整數，且不得重複
- 必須存在 `order 0` 的列，**且其 `status` 為 `Approved`** —— 否則標題與連結會被濾掉
- `order 0` 的 `link` 必須是合法網址
- `order ≥ 1` 至少須有一列通過核可（全被擋下等同 TL;DR 消失）
- `text` 不得含 `test test`、`lorem ipsum` 等測試字樣

### 行為

**驗證失敗即中止，不寫入任何檔案。**

```
🚀 Starting Content Sync...
❌ 驗證失敗，未寫入任何檔案：

  Track 1
    h15  year 應為 4 位數字，實際為「憲法第十四條規定人民有集會之自由…」
    h15  ruling_id 不可為空
  site_tldr
    order 1  text 含有測試字串「test test test」

共 3 項錯誤。請修正 SSOT 後重試。
```

**設計要點：全有全無。** 不可「跳過壞的列、寫入好的列」—— 那會讓資料悄悄變少而無人察覺，是另一種形式的靜默失敗。

## 五、更新流程

```
① 投稿
   寫作者在 SSOT 編輯（status 欄改不到）

② 核可
   編輯台確認內容 → status 改為 Approved
   退稿則改 Rejected 並填 reject_reason

③ 同步（工程師手動觸發，非部署時自動）
   npm run sync-content
     → 讀取 SSOT
     → 驗證
     → 失敗則中止並列出錯誤
     → 通過才寫入 src/data/*.json

④ 審閱
   開 PR。diff 即「這次要發布什麼」的完整清單
   Vercel 自動產生 preview 網址 ← 編輯台在此做最終確認

⑤ 發布
   合併 → 部署。部署只讀 committed json，不執行 sync
```

### 預覽方式：PR preview

編輯台以 PR 上的 Vercel preview 網址做最終確認。

**不設獨立 staging。** staging 的用途是提供固定網址給不使用 GitHub 的人；現行編輯台決策者可直接使用 GitHub，故無此需求。且 PR preview 顯示的是「本次要發布的內容」，與核可決策的對象完全一致；staging 顯示的是「目前所有 Approved 內容」，與該決策並非同一個問題。

此設計補上系統原本缺失的一環：**核可的人看得到成品。** 測試字串與佔位摘要之所以能上線，正是因為核可者只能看見試算表儲存格，無法看見網站。

## 六、不變式

以下規則不得違反。違反任一項，本次事故將以某種形式重演。

| # | 規則 | 對應的失敗 |
|---|---|---|
| 1 | **部署不得執行 sync** | 原 `build = sync && next build`，每次部署靜默重抓資料，無人看過 diff |
| 2 | **`src/data/*.json` 為產物，不得手改** | `discussions.json` 遭手改，導致「跑 sync 會讓網站倒退」 |
| 3 | **驗證失敗即中止，不得部分寫入** | 現行只印警告後繼續，等同無把關 |
| 4 | **只能有一份 SSOT** | 兩份真相導致修正無法回流、資料反向覆蓋 |
| 5 | **欄位標題必須能解析到預期欄位，否則中止** | sync 以標題字串取值，取不到則整欄靜默變空。改由程式做最長前綴比對，解析不出來就停（2026-09-01 修訂，原為「標題不得帶註解」） |
| 6 | **約定必須可被機器驗證** | 「粉紅底色＝必填」機器讀不到，無法強制執行 |

### 2026-09-01 — 推翻「欄位標題不得帶註解」

**captain 提出的反對意見**：那些中文說明（`id (給系統看的編號)` 等）是寫給學者老師看的。原設計假設 `SSOT_收集區` 只給人看、不直接餵給機器；改為單一 SSOT 之後這個假設不再成立，但**刪掉說明會讓編輯端失去唯一的欄位指引**。

**這個反對是對的，且原規則本身也違反不變式 #6** —— 「大家記得不要在標題加註解」是一條沒人在看的人為約定，無法被機器驗證。原方案把成本推給人，還留下一個會靜默失效的缺口。

**改為**：程式以最長前綴比對解析標題；解析不出來就中止並指名。規則與實測結果見第二節「欄位標題規則」。

**實測方式**（可重跑）：以 `site_tldr` 的發布 CSV 網址，配合**現行 `sync-content.mjs` 裡真正的 `parseCSV`**（非另寫的等價實作）驗證：

- CSV 內容僅含儲存格值，未包含任何註解或留言
- 現行 `parseCSV` 正確讀出 5 欄 4 列
- 依第二節還原規則組出的 `tldr` 記錄，其 `title` / `link` / `abstract` 與現行 `discussions.json` **逐字相同**
- 標題解析規則對 22 個真實標題全數正確，並對 6 個刻意設計的變形（無括號、全形空格、破折號、中括號、大小寫、`owl` 前綴混淆）皆正確，對真實錯字則正確中止

**連帶影響**：施工項目 2 取消；項目 7 的前置由 `2,3,6,6b` 縮為 `6`。
